# Validation Surface vs Distribution Surface — 2026-08-30

## Trigger

Changed Method Navigator approached a JetBrains Marketplace vendor/legal membrane. Marketplace was initially treated as the natural next step because it is the eventual distribution habitat. Current IntelliJ documentation, however, confirms that third-party plugin ZIP/JAR archives can be installed directly from disk without Marketplace publication.

This reveals a more general distinction.

## Core law

> **The cheapest surface for validating utility is not necessarily the eventual surface for distributing or monetizing the product.**

Separate:

- **Validation Surface** — the minimum external membrane needed to obtain the next decision-changing truth.
- **Distribution Surface** — the channel intended to produce ongoing discovery, installs, billing, settlement and repeat use at scale.

Do not pay the setup/legal/integration cost of the Distribution Surface merely to answer a question that a cheaper Validation Surface can resolve.

## State-relative rule

If the uncertainty is:

`Will a high-fit independent user install and find the capability useful?`

then a directly shared installable artifact can be a stronger first probe than Marketplace onboarding.

If the uncertainty is:

`Will passive Marketplace discovery generate users?`

then direct sharing cannot answer it; Marketplace exposure is required.

The experiment surface must match the uncertainty.

## Changed Method Navigator implication

IntelliJ IDEA currently supports installing third-party plugins from a local ZIP/JAR archive through Plugins -> Install Plugin from Disk.

Therefore the first external utility test can in principle be:

`verified ZIP -> explicitly authorized private share -> high-fit independent developer -> install/use/feedback`

without first requiring:

- JetBrains Vendor profile creation;
- trader/non-trader declaration;
- Marketplace Developer Agreement acceptance;
- Developer EULA selection;
- Marketplace approval;
- public listing;
- paid-plugin licensing or banking setup.

Those steps remain relevant if/when Marketplace distribution is earned.

## Sovereignty boundary remains

A direct beta is still external disclosure of a compiled private capability. It may reveal behavior and can be reverse-engineered. Sharing it with another person, identifying/contacting a tester, or publishing a download link remains a Center-holder-authorized action.

`Lower activation distance != no authorization required`.

## Validation ladder

A useful progression is:

1. private executable truth;
2. current-target compatibility truth;
3. private external utility test with one or a few high-fit independent users;
4. repeat-use / requested-use evidence;
5. distribution-channel test;
6. monetization test;
7. repeated paid return.

This prevents legal/distribution setup from preceding basic utility truth.

## Evidence semantics

A direct beta can establish:

- independent install choice;
- functional behavior on another developer's environment;
- whether the narrow transformation is useful;
- qualitative friction and repeat intent.

It cannot establish:

- passive Marketplace discovery;
- broad demand;
- willingness to pay;
- scalable distribution;
- Marketplace approval.

Do not promote evidence beyond the surface that generated it.

## Compact form

`TEST THE NEXT UNCERTAINTY ON THE CHEAPEST SURFACE THAT CAN ACTUALLY ANSWER IT.`
