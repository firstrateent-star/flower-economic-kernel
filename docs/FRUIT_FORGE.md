# Fruit Forge — from validated opportunity to passive Apify Fruit

## Purpose

Flower is not complete when it finds a validated opportunity. Its economic purpose is reached only when validated knowledge becomes a low-maintenance Fruit that can be discovered, run, paid for, measured, improved, and reused by later Fruit.

The shipping loop is therefore:

**validated evidence → private source → deterministic verification → private Apify run → cost/margin check → public release approval → passive usage → public measurement → private mutation or replication**

## Fruit Lock

Once a validated opportunity has real private source, speculative EXPAND work yields to productization. New ideas must not steal costly frontiers from a Fruit that is close to revenue.

The lock releases when the Fruit is:

- live and measurable,
- explicitly abandoned/composted,
- or blocked at a human/capability boundary that cannot be resolved autonomously.

## Three layers

### 1. Fruit Runtime

The public Actor must provide a narrow machine-readable outcome, automatic fulfillment, bounded costs, and a simple payment event.

For `Social Preview Drift Guard API`:

- one input URL → one dataset result
- deterministic `PASS | RISK | FAIL`
- direct HTTP, no browser/proxy by default
- limited permissions
- pay-per-event target
- no Standby
- honest scope: public crawler-facing state, not proprietary platform cache/render reproduction

### 2. Fruit Memory

Every Fruit carries `fruit.manifest.json` describing:

- originating opportunity
- failure/capability geometry
- monetization contract
- passive nutrient channels
- reusable organs
- public measurement signals
- mutation and replication rules

The Kernel imports manifests into Garden state. This converts source code into inherited economic memory rather than leaving it as an isolated project.

### 3. Fruit Forge

The Forge turns repeated capability families into templates only after evidence warrants reuse.

The first reusable organs are:

- safe bounded public fetch
- cross-consumer representation comparison
- deterministic risk classification
- one-unit/one-result Actor semantics
- PPE charging pattern
- limited-permission publication pattern

Do not prematurely generalize every implementation detail. A capability graduates into a shared Forge organ when it proves useful in a live Fruit or appears independently in multiple validated Fruit.

## Passive growth

Self-growth means evidence changes future private source with decreasing human effort. It does **not** mean an unreviewed public Actor rewrites itself.

Preferred loop:

1. Fruit runs and fulfills automatically.
2. Flower observes public Store usage/run-health and non-sensitive public feedback.
3. Flower diagnoses the shallowest bottleneck: discovery, reliability, price/margin, rule coverage, or product scope.
4. Flower creates a private candidate mutation or adjacent Fruit using inherited organs.
5. Deterministic/private tests run automatically.
6. Public code/pricing/release remains Center-holder gated.

## Apify monetization orientation

Prefer pay-per-event because it maps price to visible units of value and is compatible with Apify agentic discovery when current platform requirements are met.

For a per-URL checker, the primary event should represent one delivered URL audit. Initial price is a hypothesis only; benchmark a private run before publication and target a healthy margin after Apify platform costs.

The Store listing should sell the resolved decision, not the primitive. For Social Preview Drift Guard, lead with Open Graph/Twitter Card checker language but differentiate on crawler-dependent drift and PASS/RISK/FAIL automation.

## Reproduction criterion

A new Fruit is reproductive only if it inherits enough from earlier geometry to reduce at least one of:

- build time,
- measurement uncertainty,
- platform setup work,
- cost per experiment,
- distribution uncertainty,
- maintenance burden,
- human intervention.

A growing list of unrelated Actors is not reproduction. A connected library of proven organs is.
